# VideoJev-4B: дообучение и интеграция в сервис

План и инструкция: как из VideoJev-4B получить сервис, который закрывает ТЗ ForteBank
(вердикт, тип, таймкод, кадр-доказательство, норма НБРК, API за 5 минут) на одной Tesla T4.

## 1. Как устроено решение

```
.mov ──► декод 2 fps (PyAV) ──► окна 20 с, шаг 10 с (ролик ≤26 с — одним окном)
            │
            ▼
   VideoJev-4B (FP16, T4)  ── 8 вопросов-гейтов, по одному на тип нарушения (app/vj/queries.py)
            │                  вариант A = признак нарушения, B = норма, C = ситуация не возникла
            ▼
   дообученная decision head (ml/train_head.py) + пороги по типам (ml/calibrate.py)
            │  для прошедших порог типов
            ▼
   grounding того же типа в лучшем окне ──► таймкод + 1–3 кадра (pick_timecode)
            │
            ▼
   rules.CATALOG: название типа, описание, пункт НБРК № 231 / № 14 ──► JSON по разделу 10 ТЗ
```

Ключевое правило: **решение «нарушение есть» принимает только гейт** (вопрос с вариантами).
Grounding в VideoJev всегда возвращает какой-то отрезок, даже если события нет, поэтому он
нужен только для таймкода.

Код:
| Где | Что |
|---|---|
| `service/app/vj/runtime.py` | загрузка модели под T4, окна, скоринг, перехват скрытых состояний для обучения |
| `service/app/vj/queries.py` | вопросы по 8 типам |
| `service/app/vj/detector.py` | `VideoJevDetector`, политики решения, таймкод, прогрев |
| `ml/prepare_model.py` | скачать модель и сделать FP16-копию |
| `ml/score_dataset.py` | прогон датасета (с аугментациями) → `scores.jsonl` + кэш скрытых состояний |
| `ml/calibrate.py` | пороги по типам, метрики LOVO |
| `ml/train_head.py` | дообучение decision head, оценки LOVO |

## 2. VideoJev на T4: что пришлось обойти

Официальный рецепт: H200, BF16, FlashAttention 2. На T4 (Turing) нет ни BF16, ни FA2.

1. **FP16**: remote code жёстко включает `autocast(bfloat16)`. `ml/prepare_model.py` делает копию
   модели с `float16`, а веса грузятся в FP16. NaN не наблюдались.
2. **Attention**: с `sdpa` transformers включает `enable_gqa`. Memory-efficient ядро его не
   поддерживает, и SDPA уходит в math-путь с матрицей N², так что OOM начинается уже на ~7 тыс.
   токенов. В `runtime._patch_sdpa` KV разворачиваются явно и разрешено только
   `EFFICIENT_ATTENTION`. Пик памяти после этого 10–11 ГБ из 15.
3. **Triton**: при первом запуске ядра flash-linear-attention компилируются ~3 минуты. Сервис
   прогревает модель при старте (`detector.warmup`), а кэш (`TRITON_CACHE_DIR=/data/triton`)
   лежит в томе.
4. `causal-conv1d` не ставим: transformers использует torch-реализацию, на скорость это почти не влияет.

Скорость на T4 (замер): ролик 12–20 с ≈ 6–10 с на 4 вопроса. В сервисе 8 гейтов на окно и
1 grounding на найденный тип, так что 145-секундный ролик (14 окон) укладывается в ~2 минуты.

## 3. Дообучение: что реально и что нет

Официальное обучение VideoJev идёт в два этапа (`repo/scripts/train.py`):

| Этап | Что учится | Ресурсы авторов |
|---|---|---|
| 1. head warmup | только decision head (BCE для grounding, CE для QA) | 8×H200 |
| 2. joint | весь языковой бэкбон 4B + голова (+ SoftIoU) | DeepSpeed ZeRO-3, 8×H200 |

**Этап 2 на T4 невозможен**: только веса и состояния AdamW для 4B параметров занимают ~64 ГБ.
К тому же на 42 роликах модель просто переобучится.

Что делаем вместо этого:

1. **Промпты** (`queries.py`): у каждого гейта есть явная альтернатива «как правильно».
2. **Дообучение головы, аналог этапа 1** (`train_head.py`): бэкбон заморожен, скрытые состояния на
   позициях вариантов и `<|decide|>` считаются один раз (`score_dataset.py --hidden`), голова
   (2×2560→512, ~2.6 млн параметров) учится от предобученной с L2-якорем и весом положительного класса.
3. **Пороги по типам** поверх головы (`calibrate.py`), цель F2 (пропуск хуже ложного срабатывания).

Проверяли и отказались: стекинг (лог. регрессия по признакам видео) — хуже головы, с аугментациями
ещё хуже. LoRA/полное дообучение бэкбона на T4 не делали (память, 40 роликов).

### Результаты (40 уникальных роликов, leave-one-video-out)

| Способ | Recall | Ложные на нормах | Вердикт | Тип | Таймкод ±2 с |
|---|---|---|---|---|---|
| Zero-shot + пороги | 86% | 63% | 62.5% | 43% | 56% |
| Стекинг | 81% | 47% | 67.5% | 38% | 50% |
| **Голова + пороги (в проде)** | **76%** | **37%** | **70%** | **43%** | **56%** |
| «Всегда нарушение» | 100% | 100% | 52.5% | — | — |

Вывод: VideoJev даёт сигнал, но слабый. Цель (recall ≥ 90%, ложные ≤ 30%, тип ≥ 50%) не достигнута,
отсюда следующий шаг — гибрид с детектором объектов для типов «состояние сцены».

В датасете есть побайтовые дубли: Х-4 = Х-47 (один ролик, два нарушения: 57 и 68 с) и
Х-5 = Х-48. `common.DUPLICATES` сливает их, иначе leave-one-out подглядывает.

Разметка для обучения (`common.window_targets`). В разметке один таймкод на видео, поэтому:
- окно с таймкодом считается положительным;
- окна целиком до таймкода — отрицательными;
- окна после таймкода — положительными для состояний (сейф/дверь открыты) и пропускаются для событий.

Grounding учится на отрезке ±1.5 с вокруг таймкода, а для состояний — на отрезке [t, t+3].

**Ракурс** (ТЗ: финальное видео снято под другим углом). Аугментации в `common.AUGS`: отражение,
поворот + зум, перспектива. Они используются в обучении головы как отдельные примеры.
Оценка всегда идёт на исходных роликах, которых не было в обучении.

## 4. Как запустить всё по шагам (на сервере с T4)

```bash
# 0. Окружение (образ pytorch/pytorch:2.8.0-cuda12.8-cudnn9-devel)
pip install -r service/requirements.txt -r service/requirements-gpu.txt opencv-python-headless

# 1. Модель → FP16-копия (один раз, дальше интернет не нужен)
python ml/prepare_model.py --out /models/videojev-4b-fp16

# 2. Прогон датасета: оценки + кэш скрытых состояний (≈25 мин на один вариант аугментации)
python ml/score_dataset.py --videos /data/dataset --model /models/videojev-4b-fp16 \
    --out runs/full/scores.jsonl --augs none,hflip,persp --hidden runs/full/cache

# 3. Дообучение головы (оценки LOVO + head.pt на всех видео), ~50 мин на T4
python ml/train_head.py --cache runs/full/cache --model /models/videojev-4b-fp16 \
    --scores runs/full/scores.jsonl --out runs/head
# 4. Пороги поверх головы
python ml/calibrate.py runs/head/scores_cv.jsonl --out runs/head/thresholds.json
# Для сравнения — пороги без дообучения:
python ml/calibrate.py runs/full/scores.jsonl

# 5. В /models: head.pt и thresholds.json (пороги из прода — ml/artifacts/thresholds.json;
#    head.pt ~10 МБ в git не храним, он лежит на сервере в /srv/models)
```

Метрики LOVO в отчётах соответствуют критериям ТЗ. `recall` и `fp_rate` дают вердикт (25 баллов),
`type_acc_on_pos` — тип (15), `tc_mae` и `tc_within_2s` — таймкод (15).

## 5. Деплой (как сейчас на g4dn.xlarge)

Порт 80 занимает фронтенд `kassa-frontend` (Next.js). Он проксирует `/api/v1/*` и `/ui/*` на
`http://kassa:8000` в docker-сети `kassa-net`, поэтому бэкенд публикуется только на 127.0.0.1:

```bash
rsync -a --delete --exclude .venv --exclude data --exclude __pycache__ service/ ubuntu@<host>:/opt/kassa/src/
cd /opt/kassa/src && docker build -f Dockerfile.gpu -t kassa-gpu .
docker rm -f kassa
docker run -d --name kassa --gpus all --shm-size 2g --restart unless-stopped --env-file /opt/kassa/gpu.env \
  -v /srv/models:/models:ro -v /opt/kassa/data:/data --network kassa-net -p 127.0.0.1:8000:8000 kassa-gpu
docker logs -f kassa   # ждать «VideoJev готов» (~1 мин с кэшем Triton)
```

**Развёрнутая конфигурация (с 2026-10-18, «A»):** голова первого выпуска `/srv/models/head.pt` + пороги, подобранные
на оценках *этой же* головы, правило максимума: `VIDEOJEV_THRESHOLDS=/models/thresholds_head_v1_refit.json`
(= `ml/artifacts/thresholds_head_v1_refit.json`, `python ml/export_policy.py runs/head_v1/scores_augs.jsonl --policy
baseline --out ...`). Выбор — по правилу реестра (`reports/final_improvement_report.md` §3): политика zsidak (B) и
переобученные головы (soup, alt-маскирование) не прошли nested-проверку и leave-one-setup-out. Честная оценка рецепта —
строка N-base (recall 76%, ложные 53%); для новой сессии — E06h (81% / 58%).

`/opt/kassa/gpu.env`: `API_KEY`, `WORKERS`, `JOB_TIMEOUT_SEC`, `DETECTOR=videojev`, `VIDEOJEV_HEAD=/models/head.pt`,
`VIDEOJEV_THRESHOLDS=/models/thresholds_head_v1_refit.json`.

Откат (всё сохранено): `/srv/models/head.pt.v1`, `/srv/models/thresholds.json.v1` (пороги первого выпуска),
`/opt/kassa/gpu.env.v1`, образ `kassa-gpu:v1-20261017`, остановленный контейнер `kassa-v1-old`,
`/opt/kassa/src.bak-20261018`. Чтобы вернуть первый выпуск: `sudo cp /opt/kassa/gpu.env.v1 /opt/kassa/gpu.env`, затем
пересоздать `kassa` той же командой с образом `kassa-gpu:v1-20261017`.

Исправлено при деплое 2026-10-18 (всё покрыто тестами в `service/tests/test_vj_logic.py`):
- уверенность = запас над порогом, отображённый в [0.5, 1], поэтому `MIN_CONFIDENCE` больше не съедает срабатывания;
- grounding задаётся в том же упакованном контексте вопросов, что при офлайн-оценке (`detector.scoring_questions`).
  Раньше сервис спрашивал grounding в одиночку и отдавал другой таймкод: Х-20 давал 0.2 с вместо 4.25 с;
- кадр-доказательство читается с запасными путями (номер кадра, последовательное чтение). Задача больше не падает
  с «Не удалось прочитать кадр», как падала на Х-23.

Замер через публичный API на свободной T4 (2026-10-18): Х-20 (11.6 с) — 14.1 с, Х-23 (18.3 с) — 23.1 с,
Х-14 (142 с, 14 окон) — 154.8 с. Ответ сервиса совпадает с офлайн-предсказанием конфигурации A
(тип, окно, таймкод до 0.05 с). Время по этапам — в логах: `videojev <файл>: очередь …, декод …, гейты … (N окон),
grounding …; гейты: {…}; выбрано: […]`. Если на той же GPU работает что-то ещё, время растёт: при трёх обучениях
Х-14 занял 219 с.

## 6. Для сдачи: типы, ограничения, известные ошибки

### Какие типы распознаются и насколько хорошо (LOVO, тип угадан / всего в разметке)

| Тип | Что ищет модель | Результат |
|---|---|---|
| UNATTENDED_CASH | кассир уходит, на столе остаются деньги или сумка | 4/5 |
| CASH_EXPOSED_TO_VISITOR | входит посетитель, на столе открыто лежат деньги | 2/2 |
| PERSONAL_ITEMS | личные вещи, напиток, смартфон на столе кассира | 2/3 |
| UNAUTHORIZED_PERSON | второй человек за столом рядом с кассиром | 1/2 |
| NO_COUNTER | ручной пересчёт без счётчика банкнот | 0/4 |
| DOOR_OPEN | дверь кассы оставлена открытой | 0/4 |
| SAFE_OPEN | сейф оставлен открытым | 0/1 |
| CIT_PROCEDURE | приём сумки инкассатора через стол | 0/1 |

Нормы, на которых сервис ошибочно сообщает о нарушении: Х-5, Х-14, Х-16, Х-23, Х-29, Х-31, Х-39 (7 из 19).
Чаще всего это UNATTENDED_CASH, когда кассир уходит, убрав деньги (Х-23, Х-29), и CASH_EXPOSED_TO_VISITOR
в длинных роликах с клиентами.

### Ограничения

- **Обнаружение слабое**: вердикт верен на 70% роликов, пропускается ~1 нарушение из 4. Плохо распознаются
  мелкие состояния сцены (дверь, сейф) и ручной пересчёт: в кадре это несколько десятков пикселей.
- **Мало данных**: 40 уникальных роликов, у типов по 1–5 примеров. Метрики LOVO шумные (±1 видео ≈ ±2.5 п.п.).
  Главный рычаг роста — свои съёмки (FAQ 7): 10–20 сцен на тип плюс нормы, с 2–3 ракурсов.
- **Неизвестные типы** (FAQ 9): вопросы есть только для 8 типов, неизвестное нарушение будет пропущено.
- **Другой ракурс**: аугментации (отражение, поворот, перспектива) это лишь имитируют; на реальном
  другом ракурсе сервис не проверялся.
- **Одно событие на ролик**: выводится тип с наибольшим запасом над порогом. Второе нарушение в том же
  ролике (как в Х-4: 57 и 68 с) не выводится.
- **Таймкод**: для угаданного типа в пределах ±2 с в 56% случаев. Для состояний (сейф, дверь) это начало
  состояния, а не момент ухода кассира.
- **Очередь**: GPU одна, ролики обрабатываются по очереди. 145-секундный ролик идёт ~2.5 минуты, поэтому
  несколько длинных роликов одновременно могут не уложиться в 5 минут.
- **Описание** берётся из шаблона по типу (`OBSERVATIONS` + норма из `rules.py`), а не генерируется
  моделью. Это сделано намеренно: мы не утверждаем того, чего модель не видела (критерий 4).

### Что пробовали и отказались

- **Стекинг** (логистическая регрессия по признакам видео): вердикт 67.5%, хуже головы.
- **Гибрид с детектором людей** (RT-DETRv2) для уточнения таймкодов: событие «вошёл/все ушли» ловится
  точно, но не отличает нарушение от нормы, а таймкод ухудшает (MAE 5.55 → 5.83 с, ±1 с: 36% → 27%).
- **Дообучение бэкбона** (этап 2 VideoJev, LoRA): на одной T4 и 40 роликах не делали.
- **Классификатор состояний сейфа/двери по вручную отмеченным зонам**: на тестовом ракурсе зоны неизвестны
  (OWLv2 находит сейф и стол ненадёжно), камера в части роликов сдвигается; потолок выигрыша — 2–3 ролика.
- **Шаги 1–3 из отчёта `reports/Методы улучшения видеодетекции нарушений.md`** (LOVO, 40 роликов):

  | Вариант | Recall | Ложные | Вердикт | Тип | Таймкод ±2 с |
  |---|---|---|---|---|---|
  | Прод (голова + пороги, окна 20 с) | 76% | 37% | **70%** | 43% | 56% |
  | Zero-shot + калибровка по нормам (z-порог) | 86% | 53% | 67.5% | 43% | 56% |
  | Голова + калибровка по нормам | 76% | 58% | 60% | 38% | 50% |
  | Гейты, окна 10 с / шаг 5 с, + калибровка | **90%** | 63% | 65% | **52%** | 55% |
  | Атомарные вопросы да/нет + правила (+ устойчивость) | 62–100% | 58–100% | 52.5% | 33% | 14–80% |
  | Атомарные в логитах с нормировкой по нормам | 76–86% | 79–84% | 50–52.5% | 43–48% | 40–56% |
  | Вердикт прода + тип/таймкод из окон 10 с | 76% | 37% | 70% | 43% | 67% |

  Почему атомарные вопросы не сработали: на вопросы да/нет модель почти всегда отвечает «да»
  («деньги на столе» 0.99 на нормах, «дверь открыта» 0.97, «сейф открыт» 0.99), правила через min/max
  перестают различать. Ранжирующая информация у части фактов есть (AUC «вошёл человек» 0.89,
  «личные вещи» 0.86), но для вердикта её не хватает. Последний вариант улучшает только таймкод ценой
  второго прохода (длинный ролик ≈4 мин, близко к лимиту) — не внедряли.

## 7. Аудит и инструменты оценки (2026-10-18)

(эксперименты E00–E16 с протоколом), `reports/research_report.md`, `reports/generalization_report.md`,
`reports/final_improvement_report.md`, реестр `reports/experiments.csv`.

Исправлено в сервисе: детектор писал в `confidence` сырую вероятность гейта, а `analyzer.MIN_CONFIDENCE = 0.5`
отбрасывал всё ниже 0.5 — при порогах 0.05–0.45 терялись срабатывания со score в [порог, 0.5). Теперь
`confidence_from_margin` отображает запас над порогом в [0.5, 1] (тест `test_confidence_from_margin_survives_analyzer_filter`).

Политика E03e: оценка типа = (1 − p_min)^N, где p — верхний хвост гауссианы логитов «да» на окнах норм, N — число окон;
тип и таймкод берутся из правила максимума, если оно тоже срабатывает. Исправляет все три длинные нормы (Х-5, Х-14, Х-39)
и находит X-1, Х-32, Х-44; ломает Х-3, Х-19, Х-37. Файл для сервиса (не развёрнут, см. §5): `ml/artifacts/thresholds_v2.json`
(`python ml/export_policy.py runs/head/scores_cv.jsonl --policy zsidak+eventsmax --out ...`), подключается через
`VIDEOJEV_THRESHOLDS=/models/thresholds_v2.json`; детектор читает ключ `policy` (`app/vj/detector.choose`).
Оценка на 40 роликах: разница в 1–3 ролика между вариантами находится в пределах шума (E00r2).
